## 整体架构

### 设计思路

系统采用**单链路 Advisor 架构**而非多 Agent 架构，核心考量是**延迟最小化**——每次聊天请求仅需 1 次 LLM 调用，而多 Agent 方案通常需要 3-4 次。

请求处理流程分为三层：

```
用户请求
  │
  ▼
┌─────────────────────────────────────────────┐
│  Plugin 层（确定性代码规则）                    │
│  PluginService.executeBeforeRag()            │
│  → 短路返回 / 修改查询 / 继续                  │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  Advisor 链（Spring AI 自动调用）               │
│  order=0  短期记忆（MySQL 滑动窗口）            │
│  order=1  语义记忆（Milvus 向量检索）           │
│  order=2  长期记忆（用户事实/偏好）             │
│  order=3  RAG 知识检索（用户文档）              │
│  order=5  Skill 技能发现                       │
│  order=100 日志                               │
│  → 逐层增强 SystemMessage → 发送给 LLM         │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  Plugin 层（后处理）                           │
│  PluginService.executeAfterRag()             │
│  → 修改回复 / 格式化 / 注入额外信息             │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  异步后处理                                    │
│  → 存储对话到 Milvus                           │
│  → 触发事实提取（消息数 >= 4 时）               │
└─────────────────────────────────────────────┘
```

### 核心配置入口

所有 Advisor 的组装在 `MemoryConfig.chatClient()` 中完成：

```java
@Bean
public ChatClient chatClient(ChatModel chatModel, ChatMemory chatMemory,
                              VectorStore vectorStore,
                              LongTermMemoryAdvisor longTermMemoryAdvisor,
                              RagAdvisor ragAdvisor,
                              SkillPromptAugmentAdvisor skillPromptAugmentAdvisor) {
    return ChatClient.builder(chatModel)
            .defaultAdvisors(
                    MessageChatMemoryAdvisor.builder(chatMemory).order(0).build(),
                    VectorStoreChatMemoryAdvisor.builder(vectorStore).defaultTopK(5).order(1).build(),
                    longTermMemoryAdvisor,       // order=2
                    ragAdvisor,                  // order=3
                    skillPromptAugmentAdvisor,   // order=5
                    new SimpleLoggerAdvisor()     // order=100
            )
            .build();
}
```

运行时，`ChatService` 通过 `.advisors(a -> a.param(...))` 向 Advisor 链传递上下文参数：

```java
chatClient.prompt()
        .user(actualQuery)
        .advisors(a -> a
                .param("chat_memory_conversation_id", sessionId)
                .param("chat_memory_user_id", request.userId()))
        .call()
        .content();
```

## Advisor 处理链

### 设计思路

采用**责任链模式**（Chain of Responsibility），每个 Advisor 类似 Servlet Filter，拥有 `before()` 和 `after()` 两个钩子。所有自定义 Advisor 仅在 `before()` 阶段做 prompt 增强，`after()` 为透传。

选择在 `before()` 中修改 SystemMessage 而非 UserMessage 的原因：
- SystemMessage 是 LLM 的"全局指令"，注入上下文信息更符合语义
- 不干扰用户的实际输入，保持对话的自然性
- 多个 Advisor 的注入内容最终汇聚到同一个 SystemMessage 中，LLM 能统一理解

### 接口约定

所有自定义 Advisor 实现 `BaseChatMemoryAdvisor` 接口：

```java
public interface BaseChatMemoryAdvisor {
    ChatClientRequest before(ChatClientRequest request, AdvisorChain chain);
    ChatClientResponse after(ChatClientResponse response, AdvisorChain chain);
    int getOrder();
}
```

### 共同模式

两个自定义 Advisor（`LongTermMemoryAdvisor`、`RagAdvisor`）共享相同的代码结构：

1. **前置校验**：从 `request.context()` 读取 `chat_memory_user_id`，无 userId 则跳过
2. **提取消息**：通过 `extractUserMessage()` 从 prompt 中反向查找最后一条 `UserMessage`
3. **语义检索**：调用各自的服务层方法，获取 topK 条相关数据
4. **注入 SystemMessage**：遍历 prompt 的 messages 列表，找到 `SystemMessage` 并追加内容；若无 SystemMessage 则新建一个插入到列表头部
5. **构建新 Prompt**：通过 `request.mutate().prompt(newPrompt).build()` 返回不可变的新请求

SystemMessage 注入逻辑：

```java
boolean hasSystem = false;
for (int i = 0; i < messages.size(); i++) {
    if (messages.get(i) instanceof SystemMessage sysMsg) {
        messages.set(i, new SystemMessage(
                sysMsg.getText() + "\n\nUser Memory:\n" + memoryContext));
        hasSystem = true;
        break;
    }
}
if (!hasSystem) {
    messages.add(0, new SystemMessage("User Memory:\n" + memoryContext));
}
```

### 执行顺序的设计考量

| Order | Advisor | 为什么在这个位置 |
|-------|---------|-----------------|
| 0 | `MessageChatMemoryAdvisor` | 最先加载，提供最近的对话上下文，是其他 Advisor 的基础 |
| 1 | `VectorStoreChatMemoryAdvisor` | 基于当前查询语义检索历史对话，补充短期记忆遗漏的上下文 |
| 2 | `LongTermMemoryAdvisor` | 注入用户个性化信息（事实/偏好），需要在对话上下文之后以获得更好的语义匹配 |
| 3 | `RagAdvisor` | 注入知识库文档，放在记忆之后，确保 LLM 先理解用户再参考知识 |
| 5 | `SkillPromptAugmentAdvisor` | 注入可用技能列表，放在最后的业务位置，避免干扰记忆和知识注入 |
| 100 | `SimpleLoggerAdvisor` | 日志记录，放在链的最末端，记录最终的完整 prompt |

## RAG 系统

### 设计思路

RAG（Retrieval-Augmented Generation）系统让用户可以上传文档（PDF/TXT/MD），系统将文档分块向量化后存入 Milvus，聊天时自动检索相关片段注入 LLM 的上下文。

核心设计决策：
- **用户级隔离**：所有向量通过 `userId` 过滤，确保用户只能检索自己的文档
- **独立的向量集合**：使用 `@Qualifier("ragVectorStore")` 独立的 VectorStore Bean，与语义记忆的向量库分离，避免数据污染
- **异步分批向量化**：DashScope embedding API 限制单次 batch <= 10，需分批处理

### 数据模型

`rag_document` 表（MySQL）：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| user_id | VARCHAR(64) | 用户 ID |
| file_name | VARCHAR(255) | 文件名 |
| file_type | VARCHAR(16) | 文件类型（pdf/txt/md） |
| file_size | BIGINT | 文件大小（最大 20MB） |
| status | VARCHAR(16) | 状态：processing / completed / failed |
| chunk_count | INT | 分块数量 |
| error_message | TEXT | 失败原因 |
| created_at | DATETIME | 创建时间 |

Milvus 向量元数据：

```json
{
    "userId": "user123",
    "documentId": "42",
    "fileName": "设计文档.pdf",
    "chunkIndex": "0",
    "type": "rag"
}
```

### 上传流程实现

`RagService.uploadDocument()` 的完整流程：

```
1. 验证 → 文件大小（<= 20MB）、类型（pdf/txt/md）、非空
2. 创建 MySQL 记录（status=processing）
3. 读取文件内容
   - PDF → PagePdfDocumentReader 按页读取
   - TXT/MD → TextReader 作为纯文本读取
4. 文本分块
   - TokenTextSplitter: chunkSize=500, minChunkSizeChars=200, keepSeparator=true
5. 添加 RAG 元数据（userId, documentId, fileName, chunkIndex, type="rag"）
6. 分批向量化存入 Milvus（batchSize=10）
7. 更新 MySQL 记录（status=completed, chunkCount=N）
```

### 检索流程实现

`RagService.searchRelevantChunks()` 被 `RagAdvisor.before()` 调用：

```java
SearchRequest request = SearchRequest.builder()
        .query(query)
        .topK(topK)    // 默认 5
        .filterExpression("userId == '" + userId + "' && type == 'rag'")
        .build();
List<Document> results = ragVectorStore.similaritySearch(request);
```

检索结果以 `---` 分隔拼接后注入 SystemMessage：

```
Relevant Knowledge:
<文档片段1的内容>

---

<文档片段2的内容>

---

<文档片段3的内容>
```

### 文档删除

删除时需同时清理 Milvus 向量和 MySQL 记录：

```java
// Milvus 按元数据过滤删除
ragVectorStore.delete("userId == '" + userId + "' && documentId == '" + documentId + "'");
// MySQL 删除
ragDocumentRepository.deleteById(documentId);
```

## 三层记忆系统

### 设计思路

记忆系统分为三层，从短期到长期逐步抽象：

| 层级 | 存储 | 生命周期 | 数据特征 |
|------|------|----------|----------|
| 短期记忆 | MySQL（滑动窗口） | 当前会话 | 最近 N 条原始消息 |
| 语义记忆 | Milvus（向量） | 跨会话 | 历史对话的语义摘要 |
| 长期记忆 | MySQL + Milvus | 永久 | 从对话中提取的用户事实/偏好 |

三层记忆从不同维度为 LLM 提供上下文：
- 短期记忆保证对话的连贯性
- 语义记忆保证跨会话的知识延续性
- 长期记忆保证个性化回复

### 第一层：短期记忆（MessageChatMemoryAdvisor）

**配置**（order=0）：

```java
MessageChatMemoryAdvisor.builder(chatMemory).order(0).build()
```

**底层实现**：
- `MessageWindowChatMemory`：滑动窗口，保留最近 30 条消息
- `JdbcChatMemoryRepository`：持久化到 MySQL 的 `SPRING_AI_CHAT_MEMORY` 表
- 通过 `chat_memory_conversation_id` 参数区分不同会话

**工作原理**：从 MySQL 读取该会话的最近 30 条消息，作为 `UserMessage` / `AssistantMessage` 对注入 prompt。

### 第二层：语义记忆（VectorStoreChatMemoryAdvisor）

**配置**（order=1）：

```java
VectorStoreChatMemoryAdvisor.builder(vectorStore)
        .defaultTopK(5)
        .order(1)
        .build()
```

**工作原理**：将当前用户消息作为查询，在 Milvus 中语义检索最相似的 5 条历史对话片段，注入 prompt。

**写入时机**：每次 LLM 回复后，`ChatService.asyncExtractAndStore()` 异步将对话片段存入 Milvus：

```java
semanticMemoryService.storeConversationChunk(userId, sessionId, userMessage, assistantReply);
```

存储格式：

```json
{
    "content": "[User]: 用户问题\n[Assistant]: AI回答",
    "metadata": {
        "userId": "user123",
        "conversationId": "session456",
        "type": "conversation",
        "timestamp": "2026-06-05T10:30:00"
    }
}
```

### 第三层：长期记忆（LongTermMemoryAdvisor + LongTermMemoryService）

**配置**（order=2）：

```java
@Component
public class LongTermMemoryAdvisor implements BaseChatMemoryAdvisor {
    // before() 中调用 LongTermMemoryService.retrieveRelevantFacts()
}
```

#### 检索流程

`LongTermMemoryService.retrieveRelevantFacts()` 的两阶段检索：

```
1. Milvus 语义检索：根据当前查询向量匹配 topK 条事实文档
2. MySQL 回查：通过 metadata 中的 factId 回查 MySQL 获取完整记录
3. 过滤：仅保留 isActive=true 的有效事实
```

为什么需要两阶段：
- Milvus 擅长语义检索，但不适合存储完整的结构化数据
- MySQL 擅长精确查询和事务管理，存储事实的完整信息（分类、重要性、创建时间等）
- 两阶段结合了两者的优势

#### 事实提取流程

`LongTermMemoryService.extractFacts()` 在对话消息数 >= 4 时被异步触发：

```
1. 拼接对话文本（User: xxx\nAssistant: xxx\n...）
2. 构造提取 Prompt（要求 LLM 返回 JSON 格式的 facts 和 preferences）
3. 调用 DeepSeek 进行事实提取
4. 解析 JSON 响应
5. 持久化事实（含去重逻辑）：
   a. 精确匹配去重：查询 MySQL 是否已存在相同 factText
   b. 语义相似度去重：在 Milvus 中检索相似事实，相似度 >= 0.75 视为重复
   c. 无重复则新建：MySQL 存储完整记录 + Milvus 存储向量
6. 持久化偏好（upsert 语义）
```

提取 Prompt 的设计：

```
Analyze the following conversation and extract important facts and preferences about the user.
Return a JSON object with two arrays:

{
  "facts": [
    {"text": "...", "category": "personal_info|work|habit|general", "importance": 1-10}
  ],
  "preferences": [
    {"key": "...", "value": "...", "confidence": 0.0-1.0}
  ]
}

Only extract facts that are likely to be useful in future conversations.
Do NOT extract trivial or ephemeral information.
```

设计考量：
- 要求 JSON 格式输出，便于程序化解析
- `importance` 字段（1-10）用于后续检索时的排序权重
- `confidence` 字段（0.0-1.0）表示偏好的置信度
- 明确要求"仅提取对未来对话有用的信息"，避免噪音

#### 语义去重算法

`calculateTextSimilarity()` 综合两种方法：

```java
// Jaccard 相似度（关键词重叠率）占 70%
double jaccard = intersection.size() / union.size();

// 归一化编辑距离占 30%
double editSimilarity = 1.0 - (editDistance / maxLength);

// 加权结果
return jaccard * 0.7 + editSimilarity * 0.3;
```

关键词提取规则：
- 中文：2-4 字词（正则 `[一-鿿]{2,4}`）
- 英文：完整单词（正则 `[a-zA-Z]+`，转小写）

阈值 0.75 的选择：经过测试，0.75 能较好地区分"相同含义不同表述"和"不同事实"。例如：
- "用户喜欢喝咖啡" vs "用户偏好咖啡" → 相似度 ~0.85 → 视为重复
- "用户喜欢喝咖啡" vs "用户在北京工作" → 相似度 ~0.2 → 不同事实

#### 记忆整合（Memory Consolidation）

`consolidateMemories()` 定期清理重复事实：

```
1. 查询用户所有活跃事实（按重要性降序）
2. 两两比较：精确匹配 或 语义相似度 >= 0.75
3. 重复的低重要性事实标记为 isActive=false
```

### 数据模型

`user_memory_facts` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| user_id | VARCHAR(64) | 用户 ID |
| conversation_id | VARCHAR(36) | 来源会话 ID |
| fact_text | TEXT | 事实文本 |
| category | VARCHAR(64) | 分类：personal_info / work / habit / general |
| importance | TINYINT | 重要性（1-10） |
| is_active | BOOLEAN | 是否有效（软删除） |
| created_at | DATETIME | 创建时间 |

`user_preferences` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| user_id | VARCHAR(64) | 用户 ID |
| preference_key | VARCHAR(128) | 偏好键 |
| preference_value | TEXT | 偏好值 |
| confidence | DECIMAL(3,2) | 置信度 |
| source | VARCHAR(32) | 来源：extracted / manual |

## 插件系统

### 设计思路

插件系统提供**确定性代码规则**的执行能力，与 Advisor 链（LLM 驱动）互补。插件在 LLM 调用前后执行，可以：
- **短路**（SHORT_CIRCUIT）：直接返回答案，跳过 LLM（如关键词匹配的 FAQ）
- **修改查询**（MODIFIED_QUERY）：改写用户输入后再送给 LLM（如查询补全、意图纠正）
- **后处理**（POST_PROCESS）：修改 LLM 的回复（如格式化、注入额外信息）

与 Advisor 的区别：
- 插件是**确定性逻辑**（if-else 规则），Advisor 是**上下文增强**（注入信息给 LLM）
- 插件可以**短路**跳过 LLM，Advisor 不能
- 插件在 Advisor 链**之外**执行，是更外层的控制

### 接口定义

```java
public interface ChatPlugin {
    String getName();
    int getOrder();
    PluginResult beforeRag(String query, String userId);
    String afterRag(String answer, String query, String userId, PluginContext context);
}

public record PluginResult(PluginAction action, String answer, String modifiedQuery) {
    public static PluginResult continueChain() { ... }
    public static PluginResult shortCircuit(String answer) { ... }
    public static PluginResult modifyQuery(String newQuery) { ... }
}
```

### 执行流程

`PluginService` 按 order 升序执行 `beforeRag`，按 order 降序执行 `afterRag`：

```
beforeRag（升序）:
  Plugin A (order=1) → CONTINUE
  Plugin B (order=2) → MODIFIED_QUERY("新查询")
  Plugin C (order=3) → SHORT_CIRCUIT("答案")
  ↓ 如果短路，直接返回答案，跳过 LLM

afterRag（降序）:
  Plugin C (order=3) → 修改回复
  Plugin B (order=2) → 修改回复
  Plugin A (order=1) → 修改回复
```

### 运行时控制

插件支持运行时启用/禁用，优先级：运行时覆盖 > 配置文件：

```java
public boolean isPluginEnabled(String pluginName) {
    Boolean override = runtimeOverrides.get(pluginName);
    if (override != null) return override;
    return config.isPluginEnabled(pluginName);
}
```

## Skill 系统

### 设计思路

Skill 系统让 LLM 能够执行外部操作（读取文件、运行脚本等）。与插件的确定性规则不同，Skill 由 **LLM 自主决策**是否调用。

设计原则：
- Skill 元数据注入 SystemMessage，让 LLM 知道有哪些技能可用
- LLM 通过 Tool Calling 机制调用 Skill
- 严格的使用规则：简单问题直接回答，不调用 Skill

### 核心组件

1. **SkillRegistry**：技能注册表，从 classpath 自动扫描加载 SKILL.md 文件
2. **SkillPromptAugmentAdvisor**（order=5）：将技能列表注入 SystemMessage
3. **ReadSkillTool**：让 LLM 能读取指定技能的 SKILL.md 内容
4. **ShellTool**：让 LLM 能执行 Shell/Python 脚本

### 配置

```java
@Bean
public SkillRegistry skillRegistry(SkillConfigProperties properties) {
    return ClasspathSkillRegistry.builder()
            .classpathPath(properties.getDirectory())
            .autoLoad(true)
            .build();
}

@Bean
public SkillPromptAugmentAdvisor skillPromptAugmentAdvisor(SkillRegistry skillRegistry) {
    return SkillPromptAugmentAdvisor.builder()
            .skillRegistry(skillRegistry)
            .order(5)
            .build();
}
```

### Skill 使用规则

在 SystemMessage 中明确约束 LLM 的 Skill 使用行为：

```
## Skill Usage Rules (VERY IMPORTANT)
- For simple questions (time, date, weather knowledge, general knowledge, casual chat, greetings),
  answer directly WITHOUT using any skills or tools.
- For questions you can answer from your own knowledge, do NOT invoke skills.
- ONLY use skills when the user explicitly asks you to perform a specific action
  (send email, execute code, check a server, etc.) that requires external execution.
- When in doubt, answer directly first. Only use skills if a direct answer is insufficient.
- NEVER read a SKILL.md or execute shell commands for simple informational questions.
```

这样设计的原因：如果不加约束，LLM 可能会对"今天天气怎么样"这样的简单问题也去调用天气 Skill，造成不必要的延迟和资源浪费。

### ShellTool 的跨平台兼容

ShellTool 在 Windows 环境下做了兼容处理：

```java
// python3 → python
command = command.replace("python3 ", "python ");
// 去掉 bash 包装前缀
command = command.replaceFirst("^(bash(\\s+-c)?\\s+|cmd(\\s+/c)?\\s+)", "");
// .sh → .py 兼容
command = command.replace(".sh ", ".py ");
```

执行超时限制为 30 秒，防止脚本挂起。
